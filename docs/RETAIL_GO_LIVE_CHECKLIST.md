# Retail Go-Live Checklist

Living checklist tracking what's left before the retail side (arbitrage swap, deposit, withdraw, redeem-airtime) can go live. Ordered by priority — P0 items are correctness/security bugs found while auditing the live code paths, not speculative gaps.

## P0 — Fake crypto withdrawals were live on WithdrawPage.tsx, Stellar marked "recommended" (found & fixed 2026-09-04)

Prompted by a check of "is withdrawal set up as well as deposits" — it wasn't, and worse than that. `src/pages/retail/WithdrawPage.tsx`'s `ASSET_NETWORKS` listed Stellar, Tron, Polygon, Ethereum, and Bitcoin as fully selectable withdrawal networks with **no backend endpoint behind any of them at all** (confirmed: `backend/routes/stellar.py` only has deposit-related routes, nothing that signs or broadcasts a withdrawal). Worse, **Stellar was marked "recommended" for both USDT and USDC** — the top-billed option — and since asset selection auto-picked the first network in the list, it was the **default** choice for withdrawing the two most common assets.

Confirming a withdrawal on any of these networks hit a hardcoded fallback that did `await new Promise(resolve => setTimeout(resolve, 1500))` and then showed **"withdrawal processing!" as a fabricated success message — no backend call happened at all, no funds moved, nothing was verified.** A user withdrawing USDT/USDC via the default/recommended path would be told their withdrawal succeeded while literally nothing occurred.

Fixed the same way the deposit-page equivalent was fixed earlier:
- Added an `active` flag to `NetworkOption` and `ASSET_NETWORKS`. Only **Celo** (`executeValoraWithdraw`, real) and **Cardano** (`withdrawUsda`, real) are active. Stellar/Tron/Polygon/Ethereum/Bitcoin are disabled with a "SOON" badge, matching `DepositPage.tsx`'s pattern — visible so users see what's coming, but not selectable.
- Celo is now the recommended option for USDT/USDC (the one that's actually real); Stellar's misleading "recommended" tag is gone.
- Asset selection now auto-picks the first *active* network instead of blindly index 0.
- The submit button is disabled when the selected crypto network isn't active.
- The fake-success fallback now throws a clear error instead of fabricating success — defense in depth in case the (now believed-unreachable) branch is ever hit again.

**Still open:**
- [ ] Build a real Stellar withdrawal endpoint (sign + broadcast from the user's own derived Stellar account to an external address) now that Stellar deposits are real — this is the natural next piece, since the per-user wallets and treasury infra already exist.
- [ ] Audit `TradePage.tsx`/`RedeemAirtimePage.tsx`/other retail pages for the same "network list with no `active` gate" pattern — this is now the third page (after `DepositPage.tsx`) found with this exact class of bug; worth a dedicated sweep rather than finding the fourth one by accident.

## New: Real-time per-user Stellar deposit detection (2026-09-04)

Rebuilt Stellar the same way as Celo/Cardano, but it started from a much thinner and riskier baseline than either: the frontend advertised Stellar as a live, active deposit network, but the backend had **no `stellar-sdk` installed and no private key configured anywhere** — only a shared address, a memo, and a passive "check the last 10 transactions" poll. There was no way to sign, sweep, or pay out on Stellar at all. Per an explicit decision, Stellar was left active during this rebuild rather than disabled — anything deposited to the old shared address before this went live has no automated sweep/credit path and would need manual reconciliation.

**Two Stellar-specific findings that changed the design:**
- **Tether does not officially issue USDT on Stellar** — confirmed directly against tether.to's own supported-protocols page, which lists Ethereum/Tron/Solana/Celo/others but not Stellar. A "USDT" asset on Stellar would be an unverified third party using that ticker (Stellar's asset system lets anyone issue a token with any code). **Only USDC is supported on Stellar** — its official Circle issuer (`GA5ZSEJYB37JRC5AVCIA5MOP4RHTM335X2KGX3IHOJAPP5RE34K4KZVN`) was verified directly against circle.com before being hardcoded. USDT stays disabled ("Coming Soon") in `DepositPage.tsx`'s network picker for Stellar specifically — it's still fine on Celo, where Tether does officially operate.
- **A Stellar account isn't usable the instant it's derived**, unlike Celo/Cardano. It must be created on-chain (funded with a minimum XLM reserve) before it can receive anything, and each non-native asset (USDC) needs its own funded trustline before the account can hold it. This is a real, **locked** cost per user — not spent gas like Celo's top-up, but collateral that stays tied up as long as the trustline exists.

**Architecture:**
- **New secrets**: `STELLAR_MNEMONIC` (per-user child derivation via `stellar_sdk`'s `Keypair.from_mnemonic_phrase(mnemonic, index=n)`) and a brand-new `STELLAR_TREASURY_SECRET`/`STELLAR_TREASURY_ADDRESS`, generated and written directly to `.env`, never displayed. The old `STELLAR_MASTER_ADDRESS` is abandoned — no private key for it was ever available to this backend, so it could never have been signed from regardless of rebuild.
- **`backend/stellar_child_wallet.py`**: derivation + index allocation, same pattern as `celo_wallet.py`/`cardano_child_wallet.py`.
- **`backend/workers/stellar_deposit_watcher.py`**: `provision_stellar_account_sync()` is called lazily the first time a user requests a Stellar deposit address — if the account doesn't exist yet, it submits one transaction (co-signed by treasury and the child) that both creates the account and establishes its USDC trustline in one step. The watcher then polls each registered address's USDC balance (Horizon has no event log either, so this is balance-diffing like Cardano) every 10s and credits/sweeps exactly like the other two chains. Sweeps only move USDC to treasury — XLM above the reserve minimum is deliberately left on the child account, since it's locked collateral the account needs to keep existing, not spendable gas to reclaim.
- `/api/treasury/deposit-info`'s stellar branch now provisions + returns the real per-user address instead of the shared master address + memo; a failure (e.g. treasury not yet funded) now returns a clean 503 instead of a raw 500.
- **Frontend**: Stellar joins Celo/Cardano's "permanent address, no button" UI treatment in `DepositPage.tsx`; the old memo-required panel and the dangerous "fall back to a hardcoded address on error" behavior (which was already fixed for Celo but still present for Stellar) are both removed. The old session-based `initiateCryptoDeposit`/`checkDepositStatus`/`handleInitiateCryptoDeposit` code is now fully unreachable dead code, left in place for a dedicated cleanup pass rather than deleted alongside this change.

**Live status (2026-09-04, same day):** treasury (`GCNINE32IKGT7VYRYLZLAQXGNKBNCZXDHCZJ3XJKQ35LZTEYVK562GJZ`) was funded with real XLM from Bybit. **Two real users successfully provisioned real Stellar accounts with USDC trustlines through the actual app** (indices 1 and 2, confirmed live on-chain) — the deposit-address side of the pipeline is confirmed working end-to-end for real users, not just tests. Treasury is now down to ~2 XLM after those two provisions (each locks 3 XLM) — **needs topping up again before more users can onboard**; the next attempt at 2 XLM correctly failed with `op_underfunded` rather than doing anything unsafe.
- [x] ~~Fund the new Stellar treasury address with real XLM~~ — done, confirmed working.
- [x] **Cost reduced + made lazy (2026-09-04, same day, in response to the per-user cost being pushed back on)**: per-user locked amount cut from 3 XLM to 1.7 XLM (the real hard minimum for one account + one trustline is ~1.5 XLM). More importantly, `/api/treasury/deposit-info` no longer provisions anything — it just derives the address for free (a local computation, no on-chain call) and does a **read-only** check for whether it's already provisioned. The real on-chain account+trustline creation now only happens via the new `POST /api/treasury/stellar/activate-deposit`, triggered by an explicit "Activate This Address" tap in `DepositPage.tsx`, not by merely viewing the page. Verified live against production: viewing the page for a brand-new user left the treasury balance completely unchanged (confirmed via before/after balance check), and an already-provisioned real user's address still loads correctly with `provisioned: true`.

Not yet re-tested live (needs more treasury funding first to trigger a fresh provisioning attempt).

## New: Real-time per-user Cardano deposit detection (2026-09-04)

Extended the Celo permanent-address pattern to Cardano/USDA, replacing the old shared-master-wallet + manual-verify-only flow. This was a bigger step than Celo's version of the same build: **Cardano previously had zero per-user wallet isolation at all** — `cardano-USDA/wallet.py`'s `CardanoWallet` explicitly ignores its `account_index` argument ("Everyone uses the exact same Master Wallet! — Mamlaka is Custodial"), so every existing USDA/AIRT operation still runs through that one master wallet unchanged. This build only *adds* new per-user child addresses alongside it; it does not touch the master wallet's existing behavior.

- **New secret**: `CARDANO_MNEMONIC` was generated (24-word BIP39, via pycardano's `HDWallet.generate_mnemonic()`) and written directly to `.env` — never displayed in the session. **Back this up now** (same risk profile as `CELO_MNEMONIC`/`CELO_TREASURY_PK`: if lost without a backup, every child wallet and any funds in them are permanently unrecoverable).
- **`backend/cardano_child_wallet.py`** (new): derives a per-user Cardano address via CIP-1852 HD derivation (`m/1852'/1815'/{index}'/0/0`) from `CARDANO_MNEMONIC`, using pycardano's `HDWallet.derive_from_path()` → `PaymentExtendedSigningKey.from_hdwallet()`. Index allocation mirrors `celo_wallet.py` exactly (atomic counter + unique per-user doc), stored in new `cardano_child_wallet_indexes`/`cardano_child_wallet_counters` collections — kept separate from the legacy workspace-keyed `cardano_wallets` collection to avoid mixing index spaces.
- **`backend/workers/cardano_deposit_watcher.py`** (new): a persistent background task, wired into `main.py`'s lifespan alongside the Celo watcher. **Detection works differently than Celo's**: Cardano has no EVM-style event log to scan, so this watcher polls each registered address's current USDA balance via Blockfrost (reusing `cardano-USDA/usda.py`'s existing `get_balance`) and diffs it against a stored watermark — an increase is a deposit. This means **one Blockfrost call per registered address per cycle** (interval tightened from 30s to 10s on 2026-09-04 — see below), unlike Celo's constant number of calls regardless of user count — if the user base grows large, this should move to Blockfrost's webhook feature instead of polling.
- **Speed tuning (2026-09-04)**: default poll interval dropped from 30s to 10s (`CARDANO_WATCHER_INTERVAL_SECONDS`) so it doesn't stack on top of Cardano's own ~20s block time — worst case is now roughly under a minute rather than close to two. UI copy (`DepositPage.tsx`'s network picker and the "Always Watching" panel) updated from "~10 Mins"/"a minute or two" to "~30-60 Secs"/"under a minute" to match. At 10s per cycle, watch Blockfrost's rate limit (free tier is request-capped) as registered wallets grow — same scaling note as above.
- **Sweep**: tops up the child address with ADA (default 2 ADA, configurable) only if it doesn't already have enough to cover its own transaction fee, then sweeps its full ADA + USDA balance to the treasury master wallet with zero explicit outputs (`change_address=treasury` sends everything). Same best-effort philosophy as Celo — a sweep failure never affects the customer's already-credited balance.
- **`/api/treasury/deposit-info`**'s cardano branch now derives and returns the real per-user address (previously the static `MASTER_WALLET_ADDRESS`), and requires auth (it already required auth for Celo from the earlier fix).
- **Frontend**: extended all the Celo-only "permanent address, no button" UI logic in `DepositPage.tsx` to also apply to Cardano — the info panel, the always-visible manual-fallback section (which had the same regression risk as Celo's did: a stale `depositPhase`-gated condition would have hidden it forever once Cardano became permanently "listening"), the extra manual-verify amount input, and the "View Last Deposit" explorer link.
- Verified end-to-end against production: address derivation, index allocation (idempotent), and the `/deposit-info` endpoint all tested with a tagged test user and cleaned up afterward. The watcher's scan loop runs cleanly with zero registered wallets (no real user has hit the new endpoint yet). **Not yet tested with a real deposit** (unlike Celo, which was verified with real money) — do that before relying on this in production.
- **Treasury Cardano ADA balance is currently ~6.76 ADA** (plus 25.16 USDA) — enough for roughly 3 top-ups at the default 2 ADA each before it needs topping up, same funding-constraint pattern as Celo.

**Still open for Cardano:**
- [ ] Do a real end-to-end test (send actual USDA to a generated address, confirm detection + credit + sweep) the way Celo was verified.
- [ ] The existing `workers/cardano_poller.py` is dead code (relative imports that don't resolve — `backend/` has no `__init__.py`, so `from ..config import settings` fails) and was never wired into `main.py` — safe to delete once this new watcher is confirmed working, to avoid confusion about which one is live.
- [ ] `/api/cardano/on-ramp/verify` (manual verify) still exists as a fallback, matching Celo's pattern — confirm it still works correctly now that most deposits should go through the automatic path.
- [ ] Same recurring-bug audit applies here: any `SUPPORTED_ASSETS`-style list that enumerates Cardano assets should be checked for consistency, same lesson as the cUSD gap on Celo.

## New: M-Pesa (Safaricom) enabled for STK push + payouts via the Mamlaka gateway (2026-09-04)

The Mamlaka gateway itself now supports Safaricom, so `ramp.py`'s Mobile Money on-ramp/off-ramp handlers were made provider-aware instead of Airtel-only — this is the same shared gateway already used for Airtel (`AIRTEL_API_BASE_URL`/`AIRTEL_API_USERNAME`/`AIRTEL_API_PASSWORD`), not a separate Safaricom Daraja integration (no `MPESA_*`/`DARAJA_*` credentials exist in `.env`, and `services/safaricom_daraja.py`'s `DarajaService` is a different, unrelated helper for airtime procurement/merchant-balance operations against the same gateway — not STK/B2C).

Found and fixed three real bugs in the in-progress wiring (someone had started this directly in the file before this session picked it up):
- **Off-ramp (withdrawal) phone validation was still hardcoded Airtel-only** even though its `mobileMoneySP` payload field had already been made provider-aware — a user selecting M-Pesa with a real, valid Safaricom number would get rejected with "Unsupported MSISDN for Airtel payout." This was the actual blocking bug.
- **Inconsistent `mobileMoneySP` casing** — the on-ramp path sent `"airtel"` (lowercase) while off-ramp and all other code correctly used `"Airtel"`; gateways are often case-sensitive about enum-like fields, so this risked silent STK rejections.
- **Incomplete Safaricom prefix coverage** — the backend's simplified prefix check was missing legitimate ranges (074x, 0757-0759, 0768-0769) that the frontend's own validation regex already covers, meaning some valid Safaricom numbers would be wrongly rejected by the backend even after passing frontend validation.

Fixed by factoring a single shared `resolve_momo_provider_and_validate(phone_local_9, requested_provider)` helper used by both on-ramp and off-ramp, instead of two independently-maintained copies of the same logic — this is the exact "duplicated logic drifts apart" pattern that caused the cUSD asset-allowlist bug earlier in this project; using one function closes that risk here specifically.

**Not yet live-tested** (the verification step was interrupted mid-session to pivot to the Cardano build) — run a real STK push and a real payout for both M-Pesa and Airtel before considering this done. Frontend (`DepositPage.tsx`'s M-Pesa button, `WithdrawPage.tsx`'s provider toggle) was already enabled and wired to send `momo_provider` by the time this session picked up the file — confirm both still work correctly against the fixed backend.

## New: Real-time per-user Celo deposit detection (2026-09-03)

Rebuilt Celo deposit detection to work like Binance/Coinbase instead of the old "scan on poll, match by amount" approach:

- **Per-user deposit addresses**: `backend/celo_wallet.py` derives a unique Celo address per user via HD derivation from `CELO_MNEMONIC` (`m/44'/60'/0'/0/{index}`), same pattern already used for Cardano (`get_or_create_wallet_index`). `routes/valora.py`'s `/deposit/initiate` now hands out this address instead of the shared treasury address — this closes the amount-matching collision risk (two users depositing the same amount around the same time could previously be misattributed).
- **Persistent background watcher**: `backend/workers/celo_deposit_watcher.py` runs continuously (started in `main.py`'s lifespan next to the HFT bot, stopped gracefully on shutdown), scanning new blocks every ~6s for ERC-20 transfers into any address with a `listening` pending deposit — detection no longer depends on a browser tab being open or polling.
- **Real-time push**: on a match, the watcher broadcasts a `deposit_credited` event over the existing `broadcast_manager` websocket (`/ws/dashboard`) straight to that user. `DepositPage.tsx` now listens for it and flips to `credited` instantly instead of waiting for its next 4s poll (which is kept as a fallback for missed websocket messages).
- **Auto gas-top-up + sweep**: after crediting the wallet, the watcher sends a small CELO gas top-up from the treasury to the deposit address, then sweeps its full token balance back to the treasury so the funds are usable for swaps/withdrawals. This is best-effort and runs *after* the customer is already credited — a sweep failure never blocks or reverses the customer's balance, it just leaves funds sitting on the deposit address for manual reconciliation.
- **Reconciliation**: every auto-credited deposit gets a real `celoTxHash` on its `ramp_entries` row and its `pending_deposits` doc, viewable on Celoscan — the frontend's existing `ExplorerModal`/`EXPLORER_URLS` already support this.

## Live-fire test results (2026-09-03) — 4 bugs found and fixed, full loop confirmed working

Tested the real loop end-to-end: withdrew 1 real USDT from an existing user's balance via `/api/valora/withdraw` (channel "Opera MiniPay") to a second user's real per-user Celo deposit address, and confirmed it was auto-detected, credited, and swept to treasury. Found and fixed 4 real bugs along the way — **the watcher had been completely non-functional since the per-user-address redesign earlier the same day**, despite appearing "alive":

1. **Missing `0x` prefix on the Transfer-event topic hash** (`workers/celo_deposit_watcher.py`). `Web3.keccak(...).hex()` returns without a `0x` prefix in the installed `hexbytes` version (a breaking change from older versions / from stdlib `bytes.hex()` semantics). Every single `get_logs` call failed with `invalid argument 0: hex string without 0x prefix`, on every asset, every cycle. Fixed by prefixing it, same as the original (pre-redesign) code did via `w3.to_hex(...)` — which the rewrite had switched away from.
2. **The exception from #1 was swallowed and the watermark still advanced** — the per-asset `get_logs` call was wrapped in a try/except that only logged a warning, but the watermark write at the end of `_process_scan` ran unconditionally regardless of scan success. This meant the watcher *looked* healthy (its "last scanned block" kept moving every cycle) while never actually finding anything — don't trust watermark movement alone as a health signal; check for the absence of scan errors specifically.
3. **`eth_getLogs` exceeded the RPC's result cap** (`query exceeds max results 20000`) once the watermark was manually rewound to rescan the missed window — a ~650-block range on a busy contract like USDT returned more logs than Forno allows in one call. Fixed by always scanning in bounded chunks (`SCAN_CHUNK_BLOCKS`, default 150) rather than one large range — this also makes the watcher resilient to any *future* gap (restart, deploy, downtime), not just this one-time rewind.
4. **Gas top-up for the sweep was a fixed guess (0.01 CELO) instead of calculated from the live gas price** — at the time of this test the sweep actually needed ~0.0405 CELO (gas price was 202.5 gwei), so every sweep would have failed with `insufficient funds for gas`. Fixed to calculate `gas_price × SWEEP_GAS_LIMIT × 1.25` buffer dynamically, with a clear error if the treasury itself can't afford the top-up.

After all four fixes, the missed deposit was manually reconciled (rewound the watermark, re-ran the scan, then re-ran the sweep) and confirmed landing in the treasury (USDT balance now 4.9). **Treasury CELO is now down to ~0.159** after this test's gas costs — at ~0.04–0.05 CELO per sweep, that's only ~3 more deposits before it runs dry (crediting would still work; sweeping would start failing again). ## Security hardening — withdrawal limits & audit log (2026-09-03)

Started hardening Celo money-movement after a security review found two high-severity gaps: no withdrawal limits (a stolen session could drain a user's entire crypto balance instantly, to any address) and no dedicated audit trail for signing events (only regular business records in `ramp_entries`, not designed for incident investigation).

- **`backend/celo_audit.py`** (new): `log_celo_audit_event(db, event, **fields)` — append-only writes to a new `celo_audit_log` collection. Never raises (a logging failure must not block a money-moving operation, but is itself worth alerting on separately as a visibility gap).
- **Withdrawal limits** (`routes/valora.py`): `CELO_MAX_WITHDRAWAL_PER_TX` (default 500) and `CELO_MAX_WITHDRAWAL_PER_DAY` (default 2000), per-asset, both env-configurable without a redeploy. The daily limit is a rolling 24h window computed from `celo_audit_log`'s own `withdrawal_broadcast` events (not from `ramp_entries`, which uses inconsistent channel names across withdrawal paths). Every withdrawal now logs `withdrawal_requested`, and either `withdrawal_blocked_limit` (with the reason and limit), `withdrawal_broadcast` (with the real tx hash), or `withdrawal_failed` (with the error). Verified against production DB with a tagged test user: an oversized single withdrawal and a request that would exceed the daily total were both correctly blocked, with the audit trail written and cleaned up.
- **Sweep audit trail** (`workers/celo_deposit_watcher.py`): `_sweep_deposit_sync` now returns a result dict (topup tx hash/amount, sweep tx hash/amount) instead of only logging to stdout, and `_process_scan` writes `sweep_completed` or `sweep_failed` to the same audit log.

**Still open from the security review — not done yet:**
- [ ] No app-level "kill switch" to pause withdrawals/sweeps instantly if something looks wrong (the HFT bot has one in `Brain_Engine/bot.py`; money-movement code doesn't).
- [ ] `CELO_MNEMONIC`/`CELO_TREASURY_PK` still sit in a plaintext `.env` on the same server as the public web app — the single biggest risk. Needs a real secrets manager (AWS/GCP Secrets Manager, Vault) — an infra decision, not something fixable from application code alone.
- [ ] No cross-check between MongoDB balances and actual on-chain treasury holdings — a DB compromise could let someone fabricate a balance and withdraw it as real crypto. Needs a periodic reconciliation job.
- [ ] No cold/hot wallet split or multisig for the treasury — one private key controls all consolidated funds.
- [ ] Withdrawal limits are currently global constants, not per-user-tier — consider KYC-tier-based limits later (e.g., higher limits for more-verified users).
